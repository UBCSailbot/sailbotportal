## Problems and contracts

The 20 November review reproduced two database flaws and two stale-state bugs. Leads could change their own permission-bearing profile fields and impersonate other actors in audit events. A same-application refresh could leave an old Docs input beside a newer saved link. URL filter changes could leave controls describing a different cohort.

### Phase 1: database boundaries

Create `supabase/migrations/20261120090000_profile_permissions_and_audit_writes.sql`. Add the `profiles_guard_permissions` BEFORE UPDATE, FOR EACH ROW trigger to `public.profiles`, calling `public.guard_profile_permissions()`. Its function is SECURITY INVOKER with an empty search path: the database caller stays `authenticated`, so it cannot bypass the guard through an elevated function owner. Reject changed `role`, `team_id` or `subteam_id` with SQLSTATE 42501 for `anon`/`authenticated` callers unless `public.is_admin()` says the caller was already an admin. Compare OLD and NEW using IS DISTINCT FROM, including null changes. Ordinary self-service fields and unchanged permission fields remain writable under existing RLS. Existing admins, service-role fixture/invitation administration, and database migration roles retain permission-management access. Existing RLS still controls which profile rows may be updated. Revoke direct execution of the trigger function from PUBLIC, anon and authenticated; trigger execution still works.

In the same additive migration, drop the `leads insert own team events` policy and revoke INSERT on `public.application_events` from PUBLIC, anon and authenticated. Existing `public.log_status_change()` is SECURITY DEFINER, so legitimate lead/admin status updates still append their actual actor and old/new status atomically. Service-role maintenance can still insert historical fixtures. No row is deleted or rewritten. Authenticated admins also cannot insert arbitrary audit events through PostgREST.
